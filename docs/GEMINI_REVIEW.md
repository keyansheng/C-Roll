# Gate: code review handoff for Gemini

Review the implementation at commit **`226fb73`**, app version **0.1.2 (build 3)**. This document records context for an independent critique; it does not establish that the design is correct. Inspect the source and challenge the assumptions below. No application code was changed while preparing this handoff.

## Purpose and current result

The user wants an iPhone camera app that captures Bayer RAW photos repeatedly, develops them on-device, and encodes video while avoiding the normal processed-video recording pipeline. The inspiration is [Log Cam](https://apps.apple.com/us/app/log-cam-open-gate-by-raw-cam/id6766185881). The immediate performance goal is sustained **30 fps at the full 4032 × 3024 sensor frame** on **iPhone 16 Pro**.

Gate is an original native SwiftUI prototype, not a completed feature-equivalent clone. It captures Bayer RAW through `AVCapturePhotoOutput`; it does not record the standard video feed and apply a flat-looking filter. It still uses Apple's RAW decoder and calibration through `CIRAWFilter`.

## Current pipeline

```text
Physical rear wide camera at 1×, photo session
    → fresh Bayer RAW photo request, speed priority, no processed companion
    → retained AVCapturePhoto and its pixelBuffer + metadata
    → CIRAWFilter, explicit development settings
    → portrait orientation, center framing, scale to selected long edge
    → custom Gate Log or Rec.709 OETF
    → CIContext.render into pooled 8-bit BGRA
    → AVAssetWriter input / pixel-buffer adaptor
    → MOV and JSON sidecar

Before recording:
    developed RAW → monitor transform/assist → CGImage → SwiftUI

During hardware recording, if the preview connection is available:
    same capture session → AVCaptureVideoPreviewLayer → UIKit surface
    RAW monitor render and per-frame CGImage publication are skipped

If the optional preview cannot be connected:
    RAW monitor rendering continues as a fallback
```

The native recording preview is Apple's processed image, not an accurate representation of the recorded custom log signal. The UI labels it `SYSTEM PREVIEW` and disables RAW gamma/zebra/false-color controls while that branch is active. Simulator mode supplies synthetic images and continues rendering them for monitoring.

### Queue and ownership intentions

- `captureQueue` is serial and owns session/device changes, the timer, request map, budget, recording flags, and timing counters.
- `processingQueue` is serial and owns development, rendering, and writer operations. Each request supplies a settings snapshot and a recorder reference.
- Published UI properties are updated on the main queue. `CameraController` is declared `@unchecked Sendable`; this is an assertion of synchronization, not compiler verification.
- Each photo request has new settings and a retained delegate. The photo itself remains captured by the processing closure while its inner-pointer RAW pixel buffer is in use.
- A slot is intended to remain occupied until both processing and the final capture callback finish. The current limit is **two slots**, covering all stages, rather than two independent queues of two frames each.
- The writer pool has an allocation threshold of four buffers. Writer pressure or non-monotonic timestamps cause a skipped append rather than an unbounded queue.

Treat these as intended invariants and audit whether every normal, error, timeout, and background path actually preserves them.

### Scheduling and take boundaries

`startTimer()` schedules a fixed-cadence `DispatchSourceTimer`: six requests per second while idle, the selected target while recording. `tick()` skips an opportunity if the total budget is full. Releasing a slot does not immediately submit a replacement request; the next timer event supplies the next opportunity.

`toggleRecording()` pauses idle scheduling and sets a pending start. `startTakeIfDrained()` waits for the budget to become empty before attempting to connect the preview and creating a recorder. The layer connection is explicitly formed on `captureQueue` inside a session configuration transaction. The UI only hosts and sizes the layer. Subsequent takes reuse the connection; it is not detached at every normal stop.

Stopping cancels the timer and drains requests before finalization. A five-second timeout can clear the request map and replace the budget. Retry waits for outstanding work, rebuilds a failed session, and disables the optional preview for that controller session if capture failed while the connection was present.

### Timing and diagnostics

Movie PTS comes from `AVCapturePhoto.timestamp`, relative to the first accepted sample. Gaps remain in the movie rather than compressing elapsed time. The final session end adds one target frame interval after the last accepted sample. Recording-clock UI publication is limited to four updates per second; FPS/ISO/shutter publication occurs roughly once per second.

JSON includes `frames`, `duration`, `averageFPS`, output dimensions, the input/profile, and a `performance` object. That object currently reports:

- Mean request-to-photo-processing-callback latency, including dispatch back to the capture queue.
- Mean wait to start work on `processingQueue`.
- Mean RAW development/render and encoder-append submission time for successfully written frames.
- Whether RAW preview rendering was enabled for recording frames, preview branch, slot bound, and skipped capture/encoder opportunities.

These are application-level wall-clock measurements. They do not separate CPU and GPU execution or measure asynchronous encoder completion. Failed/skipped writes are excluded from the successful-frame timing means. The `skipped` counter combines opportunities and encoder/timestamp skips; it is not an independently measured count of missing sensor frames. Timer events that never run are not separately counted.

## Review priorities and open hypotheses

Please examine these areas independently. Questions below are review targets, not confirmed root causes.

### 1. Why does throughput plateau below 30 fps?

Inspect `tick()`, `received()`, `completeFrame()`, `releaseIfFinished()`, and `MovieRecorder.append()` together. With two total slots, RAW callback latency plus queueing/rendering can limit submission even when an individual GPU render is fast. For illustration, a mean 80 ms slot lifetime could bound a two-slot pipeline around 25 completions/s; this is not a measurement of Gate. Fixed timer polling may add another wait after capacity becomes free.

Determine whether the rate is limited by photo delivery, capture-slot lifetime, timer quantization, serial processing, RAW decoder setup, GPU work, pixel-buffer allocation, encoding pressure, or preview/session format changes. Propose instrumentation and a controlled comparison before prescribing larger buffer counts or a different timer. A larger queue alone cannot fix a processing stage whose sustained service time exceeds the frame interval.

Check the cost of creating a `CIRAWFilter` per frame, selecting decoder 8, scaling inside the decoder and again in `frame()`, half-float working intermediates, and disabling intermediate caching. Determine whether unnecessary graph evaluation, copies, rotations, or color conversions remain. There are no Instruments traces proving any one of these is the dominant cost.

### 2. Capture callbacks, timeouts, and stale work

Audit the two completion flags, all delegate-error paths, and ownership when the five-second stop timeout clears `requests` and resets the budget. Can late callbacks or processing completions update counters, report an error, or release capacity belonging to a later take/rebuilt session? Are delegate and pixel-buffer lifetimes maintained through cancellation? Do pending-start and stop timeout IDs cover all stale-work paths, or only the timeout closures?

Consider a capture that produces no processing callback, a final callback that arrives first, a slow GPU render, a timeout followed by Retry, and backgrounding during a pending start. Verify that recovery cannot exceed the intended memory bound or block the UI indefinitely.

### 3. Preview graph and hardware settings

Verify that manually connecting a preview to a running `.photo` session preserves the active camera format, RAW pixel formats, supported photo dimensions, and capture readiness. `rawFormat` and photo dimension configuration are selected at setup; examine whether they must be revalidated after graph changes. A connection's existence is not proof that it is delivering visible frames.

After the first take, the connected preview remains attached while hidden during idle RAW monitoring. Inspect whether this changes resource use or session behavior. Check portrait rotation and `resizeAspectFill` against the RAW crop and field of view. Audit preview-layer/session ownership across view teardown, backgrounding, Retry, and session reset.

Check ISO/shutter clamps, auto-exposure bias, focus locking, and sensor white-balance gains alongside RAW neutral-temperature settings. Review every AVFoundation property's prerequisites: some invalid configurations raise Objective-C exceptions that a Swift `do/catch` will not catch.

### 4. Concurrency and recovery

Audit `@unchecked Sendable`, all cross-queue property reads/writes, notification callbacks, the async writer completion, and main-thread UI bindings. Confirm that configuration snapshots protect all mutable state they need to protect.

Inspect interruption recovery separately from runtime-error recovery. In particular, interruption-end handling checks `active`, while stopping for an interruption sets it false. Determine whether the intended behavior is automatic recovery or manual Retry, and whether the current UI/state transitions reliably implement it.

### 5. Actual image quality and color correctness

`CIRAWFilter` disables baseline exposure, shadow bias, boost, gamut mapping, and supported sharpening/local-tone/detail adjustments. Neutral temperature is applied during development. Working space is extended linear sRGB (Rec.709 primaries), working format is `RGBAh`.

Gate Log is a custom per-channel curve:

```text
encoded = log2(1 + 15 * max(0, linear)) / 4
linear  = (2^(4 * encoded) - 1) / 15
```

This is not Apple Log, S-Log3, or a calibrated cinema-camera profile. Linear 1 maps to code 1; values above it exceed the current normalized 8-bit output range. The implementation does not promise additional captured dynamic range. Both HEVC and ProRes currently receive **8-bit BGRA**. A higher-precision ProRes container cannot restore lost input precision.

Review whether the chosen RAW settings really yield the assumed scene-linear signal on iPhone 16 Pro, including highlight behavior and decoder differences. Check primaries, transfer functions, writer defaults/tags, YCbCr conversion/range, and whether implicit conversions alter log code values. Gate Log has no standardized QuickTime transfer tag; its description and JSON identify the custom curve. Rec.709 output is explicitly tagged.

Synthetic neutral-pixel checks do not validate real camera matrices, saturation, highlight recovery/clipping, white balance, spatial artifacts, or temporal consistency. Recommend physical RAW-reference/color-chart tests. Review the inverse LUT, the use of a display color-space relabel for RAW monitoring, and the false-color thresholds.

### 6. Files, error visibility, and tests

Inspect `MovieRecorder.finish()` and `refreshClips()`: JSON serialization/write uses `try?`, while the library requires a JSON sidecar before exposing a movie. Determine whether a finalized MOV can be reported as saved yet disappear from the library if metadata writing fails. Examine empty-take cleanup, encoder failures, disk-full behavior, and preserving the original camera error during finalization.

Review whether the tests protect behavior rather than just restating policies. The native preview, real photo delegate lifecycle, camera session reset, and physical capture cadence are not exercised by the synthetic simulator route. Identify meaningful tests for any proposed correction and distinguish tests that require a phone from portable checks.

## Regression history: avoid overclaiming the cause

Version 0.1.1 introduced several changes at once: a standard preview connected by the UI during startup, rotation changes from layout, forced 1/30-second video frame durations, and a three-slot budget. The user reported a startup failure with “The operation could not be completed.” No error domain/underlying code was available in that screenshot.

Version 0.1.2 removed the forced sensor-cadence override, restored two slots, moved preview connection/rotation control to the capture queue, deferred connection until idle work drains, improved error detail, and added session rebuild/fallback behavior. The user subsequently reported successful recording at the rates above. This supports recovery of functionality, but **does not isolate which 0.1.1 change caused the startup failure**. Do not present a suspected cause as proven.

## Build, test, and profiling reproduction

See [README](../README.md) for phone signing/setup and grading instructions. The project has no third-party dependencies; it was built using Xcode 27 with iOS deployment target 18 and Swift language mode 5. Install Apple's Metal compiler component if Xcode reports it missing.

```sh
# Portable tests; does not boot a simulator.
swift test

# Physical-device Release archive; does not install or boot a simulator.
xcodebuild -project Gate.xcodeproj -scheme Gate -configuration Release \
  -destination 'generic/platform=iOS' -derivedDataPath build-device \
  -archivePath build/Gate-review.xcarchive CODE_SIGNING_ALLOWED=NO archive

# Compile the integration target without running it.
xcodebuild -project Gate.xcodeproj -scheme Gate -configuration Debug \
  -destination 'generic/platform=iOS Simulator' -derivedDataPath build \
  CODE_SIGNING_ALLOWED=NO build-for-testing
```

`xcodebuild test` against a named simulator runs/boots that device. The user previously asked to stop all simulators; none were started for the final 0.1.2 checks. Leave any simulator used for future review stopped when finished.

IPAs were packaged locally as unsigned `Payload/Gate.app` ZIPs after successful Release archives. No valid signing identity was configured. Local `build/` artifacts are ignored by Git; IPA filenames are not reproducible committed binaries. Signing is required for installation.

For a phone benchmark, record the app version, actual output dimensions, codec/bitrate/profile, shutter/ISO, thermal state, preview branch, and capture target. Keep scene lighting and settings comparable across implementations. Run both short and sustained takes, inspect MOV sample timestamps/durations and the JSON timing summary, and profile CPU/GPU/encoder/memory pressure. Separate preview smoothness, request rate, delivered RAW rate, accepted encoded-frame rate, and playback cadence. Verify that any apparent 30 fps improvement consists of unique RAW exposures rather than duplicated frames or compressed time.

## Requested critique format

Lead with actionable findings in severity order. For each finding give the file/method (and line if useful), a concrete trigger, the consequence, supporting source evidence, and a proposed correction plus validation. Mark hypotheses and hardware-dependent claims explicitly. Separate confirmed defects, likely performance bottlenecks, missing evidence, and intentional prototype limitations.

Finish with a short, prioritized plan to reach sustained 30 fps at full 12 MP while preserving RAW-derived image quality and reliable take lifecycle behavior. Critique the implementation independently; do not assume the observations or questions in this handoff are exhaustive or conclusive.
